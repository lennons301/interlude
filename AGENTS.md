# Interlude

## Project Overview

Interlude is a self-hosted, agent-first development platform. You dispatch tasks to AI agents via a mobile-friendly web UI, monitor their progress in real-time, and receive results as PRs.
It is also a second executor of the estate's ticket-loop contract: tickets labelled `ready-for-agent` are picked up, implemented in a container, reviewed by a fresh-context reviewer pass, and auto-merged or parked for human sign-off (operator runbook: `docs/runbook.md`).

## Tech Stack

- **Framework:** Next.js 16 (App Router), React 19, TypeScript, served through `custom-server.js` (Host-header routing for task preview subdomains)
- **Database:** SQLite via Drizzle ORM + better-sqlite3 (WAL mode, foreign keys on)
- **UI:** Tailwind CSS + shadcn/ui (dark theme default)
- **Real-time:** Server-Sent Events (SSE)
- **Agent runtime:** one Docker container per task (`Dockerfile.agent`), driven with dockerode; harness adapters under `src/lib/harness/`, execution lanes in `lanes.yaml`
- **Integrations:** GitHub App (webhooks, issue sync, PRs, short-lived git tokens), Discord bot (discord.js)
- **Secrets:** Doppler (`interlude/dev` locally, `interlude/prd` on the VPS)
- **Deployment:** Docker Compose (Caddy + app) on a Hetzner VPS, deployed from `main` by `.github/workflows/deploy.yml`
- **Testing:** Vitest (+ Testing Library, jsdom)
- **Linting:** ESLint (Next.js config)
- **Package manager:** pnpm

## Commands

```bash
doppler run -- pnpm dev     # Start the orchestrator locally (secrets from Doppler interlude/dev)
pnpm test                   # Vitest, single run
pnpm lint                   # ESLint
pnpm build                  # Production build
npx drizzle-kit generate    # Generate a migration from schema changes (see Database for the caveats)
npx drizzle-kit push        # Apply the schema to the local SQLite DB
```

`pnpm lint` fails on `main` with pre-existing errors (known baseline). Lint
only the files you changed — don't fix or be blocked by baseline errors in
files you didn't touch.

## Local development (outside Docker Compose)

Local dev runs the orchestrator via `doppler run -- pnpm dev` — orchestrator secrets live in the Doppler `interlude/dev` config, not a `.env`. Two things Compose provides on the VPS that you must set up by hand locally:

- **Agent-container network:** run `docker network create interlude` once. Agent containers attach to the `interlude` network, which Compose creates on the VPS but `pnpm dev` does not — without it, task runs fail with "network interlude not found".
- **Claude auth for agent containers:** set `CLAUDE_CODE_OAUTH_TOKEN` (in `interlude/dev`) to a token minted with `claude setup-token` — otherwise the agent errors with "Not logged in". This env token (or `ANTHROPIC_API_KEY`) is the only way Claude auth reaches an agent container; the legacy `CLAUDE_CREDENTIALS_PATH` credentials-file mount was removed in issue #28 (see the "no host mount" convention below).

## Key Conventions


- IDs use ULIDs (via `ulidx` package, helper at `src/lib/ulid.ts`)
- Database timestamps use `timestamp_ms` mode (JavaScript Date objects)
- API routes return JSON, validate input, return appropriate status codes
- Components are client components (`"use client"`) when they need interactivity
- File structure: pages in `src/app/`, components in `src/components/`, utilities in `src/lib/`, database in `src/db/`
- Preview uses subdomain routing: `task-{shortId}.interludes.co.uk` (controlled by `DOMAIN` env var, path-based fallback when unset)
- `DOMAIN`'s production source of truth is Doppler (`interlude/prd`): the app reads it via `doppler run`; the deploy renders `caddy.env` from the same config for Caddy. Never hand-set `DOMAIN` in the VPS `.env` (issue #25)
- Container network aliases match subdomain prefixes for Docker DNS resolution
- The `interlude` Docker network is **external** to the compose stack (issue #190): it is the compose *default* network renamed, so `compose down` used to remove it and `up` recreate it with a new ID, while parked agent containers still referenced the old one — their `docker start` then failed `network <old-id> not found` forever, so a blocked run survived a restart but never a deploy. The deploy creates it idempotently; `startContainer` also reattaches (with the container's recorded aliases, which the preview subdomain depends on) and retries once, for containers already orphaned
- The deploy **asserts the SHA it deployed** (issue #189): `deploy.yml` runs `set -euo pipefail`, retries the anonymous `git pull` (the box's HTTPS remote has no credential and GitHub rate-limits it), and fails if `git rev-parse HEAD` != `github.sha`. Without that, a failed pull was non-fatal and `compose build` reproduced the *identical* cached image while every health check passed — two commits reported success while prod sat 4.5h behind
- Caddy `on_demand_tls` provisions certs per-subdomain; validated via `/api/internal/validate-subdomain`
- GitHub App provides webhook-driven issue→task creation (label `interlude` triggers task)
- Draft PRs auto-created on first branch push, marked ready for review on completion
- GitHub App is REQUIRED for git auth — agent containers clone/push using short-lived App installation tokens (no PAT). Issue sync + PR features still degrade gracefully if webhook/installation are partially configured.
- Reviewer identity: the review pass returns a structured verdict and the **orchestrator** posts the PR review using `REVIEWER_GH_TOKEN`; the PAT never enters an agent container (issue #17). Its canonical home is Doppler `platform/prd`, and it is **mirrored** into `interlude/prd` because the orchestrator's service token is scoped to one config — **rotation must update both places**.
- Git credential helper in agent containers reads a per-exec `GIT_AUTH_TOKEN` (minted fresh from the App); no token is persisted in `.git/config`.
- Agent containers get **no host bind mount** (issue #28): everything they need is granted deliberately and exec-scoped — the `interlude` Docker network, a fresh `GIT_AUTH_TOKEN`, and Claude auth via `CLAUDE_CODE_OAUTH_TOKEN`. There is no host `~/.claude` mount, so a container cannot read or write the host user's Claude config/history/credentials, and the image's own `/home/node/.claude` (the skill links, etc.) survives unshadowed. The rationale lives at the mount site in `src/lib/docker/container-manager.ts` — read it before adding any `Bind`.
- Skills reach the agent **image at build**, through the open Agent Skills standard (issue #215). `Dockerfile.agent` installs Matt Pocock's `mattpocock/skills` with the Agent Skills installer (`npx skills add`), **pinned** by the `/tree/<tag>` URL form to the ref its `SKILLS_REF` build arg names (the `add` command has no ref flag; the bare source installs `main`), at global scope for the Claude Code, Codex and OpenCode agents: the canonical folders land under `/home/node/.agents/skills/<name>/SKILL.md` — the standard location Codex and OpenCode read natively — and `/home/node/.claude/skills/<name>` links to them for Claude Code, which is why all three agents are targeted (given a single target the installer copies into that agent's directory and the canonical folder never exists). This replaced #60's `claude plugin install` at every container setup, which was Claude-only by construction, unpinned (an upstream release could change a pass mid-day) and cost ~9s of wall-clock per start (8.7s measured on the pre-#215 image, warm, live network); the setup script runs no `claude plugin` command now, pinned by a test. A skill installed this way is a plain skill, not a namespaced plugin, so `/grill-me` and a `workflow:tdd` label resolve by exact name or not at all — so the build **asserts** that every schema-declared session skill (`SESSION_SKILLS`) and every vendored workflow under `docs/agents/workflows/` (by file stem) is present, linked for Claude Code and pinned to the ref in the installer's lock file. That list lives in the Dockerfile's `REQUIRED_SKILLS` arg because the build context is the Dockerfile alone, and `image-builder.test.ts` pins it to both sources: a session skill or workflow added without being listed fails the test, a listed skill the installer skipped fails the build. The pinned ref is stamped on the image as the `co.interlude.agent-skills-ref` label from the same build arg (one statement of the ref, so a manual `docker build` stamps it too); `ensureImage` reports it off the inspect its staleness check already makes (no second daemon round trip, #151) as the container is created, and the turn manager writes it to `runs.skillsVersion` (first-write-wins — the implement pass's) and the feed's system note, so the pass reports nothing and nothing a pass does can blank the trail. Staleness needs no new mechanism: the Dockerfile hash already covers the arg, so bumping `SKILLS_REF` rebuilds the image. To bump: read upstream's CHANGELOG diff for every skill in `REQUIRED_SKILLS`, change the arg, and let the build re-assert the set. The vendored workflow files stay harness-neutral, and the external skills are neither forked, wrapped nor vendored (#196's rule)
- Webhook endpoint: `POST /api/webhooks/github`
- GitHub library: `src/lib/github/` (client, webhooks, issues, pull-requests)
- Discord bot (optional; degrades gracefully when unconfigured) maps each project to one channel via `!link <project>` / `!unlink`; new channel messages create tasks, replies deliver follow-ups
- Discord lifecycle embeds: queued / completed / failed, plus an idle "agent finished a turn" notification (react ✅ to complete the task, reply to continue)
- Triage (issue #23): `issues.opened` on a registered project marks the issue `needs-triage` (the label is the queue); a short read-only pass (`kind: triage`, no run, ~$2 + hard turn cap) returns `TRIAGE: recommend | needs-info | ready-for-human` and the orchestrator applies fixed consequences. Triage can never apply `ready-for-agent`, edit bodies, or close issues — arming needs a human label click or an explicit Discord "yes" (reply to the recommendation embed), and the route is recorded on the issue
- Triage suggests a tier (issue #200): a raw issue reaches the loop carrying a tier without anyone transcribing one. The exit gains an optional `TIER: light | standard | heavy` line under the `TRIAGE:` line, parsed by `parseTriageExit` (clamped through `normalizeModelTier`, so a pass may pick a tier but never name a model; an absent or unrecognised value leaves the suggestion null without touching the verdict, and a malformed exit fails closed exactly as before; the `TIER:` marker is matched in its own upper case where `TRIAGE:` is not, because a missed exit marker fails the exit closed while a false tier match would silently consume the first line of an assessment). It is stored on its **own column**, `tasks.triageTier`, because `triageResult` is *consumed* when the sweep applies the exit (a re-labelled issue must get a fresh pass, not a replay) while the tier has to survive that and be read at **claim**, which may come hours later on a label click or a Discord "yes". `finishTriagePass` writes the exit, the tier and `completed` in **one statement**: the sweep gathers a pass to apply by its stored exit and the claim reads the tier off the newest `completed` pass, and those select the same rows only if holding an exit and being completed are the same fact — written as two statements, a throw between them left a `failed` row holding a good exit, so the embed named one tier and the run got another; a triage row is `failed` only when the pass died, and that row's catch-written unparseable result is applied fail-closed and skipped at claim. `chooseRunTier` (`triage.ts`) is the one statement of precedence — the body's `model:` directive always outranks the stored suggestion, which applies only where the body states none — and both the claim and the recommendation read it, so the tier the embed names is the tier the run gets. The recommendation embed and the assessment comment state the tier the run will use; when neither chose one the embed *names* the configured default (the executor resolves it through `resolveLane` against the primary lane, the resolution the pass makes at start unless routing has moved it off a walled lane (#173/#176), the same boundary #171's gate reads at — a priced lane resolves an unset tier to `standard`, so the model-choice step alone would name a tier the run does not use; the sentence is the reducer's `describeDefaultTier`, handed the resolution as data, and an environment pinning a raw model id is said to pin a model rather than printed as a tier) while the pure reducer's comment can only say "the configured default"; the claim comment says whether the run took the ticket's tier or triage's. At claim the *newest completed* triage pass decides, a null included — a re-triage that omitted the line means the default, not an earlier pass's judgement about an earlier body — while a pass that died says nothing. The triage rubric is the tracker contract's own words, pinned criterion-for-criterion by `tracker-contract.test.ts` so the two producers cannot diverge. Triage still cannot arm, edit bodies or close issues, and there is no line it could write that names a lane
- Draft PR is auto-created on first branch push for **any** task origin (issue, Discord, or UI) — not only issue-linked tasks — and marked ready for review on completion
- Discord library: `src/lib/discord/` (client = gateway + message/reaction routing, notifications = embeds)
- Non-text contrast (issue #142): `--fl-mark` is the quiet neutral for marks that are **not text** — the focus ring (`FOCUS_RING`) and every status dot — because those owe WCAG's 3:1 floor and `--fl-ink-3` misses it on the light ground (2.44:1). `--fl-ink-3` stays the quiet *ink*, for text only. A component that paints a background in ink-3 fails `src/components/__tests__/fleet-tokens.test.ts`, which also checks both themes' values against ground/surface/card and holds the light palette's two copies (a media query can't be OR'd with a selector) to being identical
- Tasks archive read path (issues #120, #142): the list is bounded by recency and nothing paginates it, so the kind filter is applied **in SQL** — `readTaskList` (`src/lib/tasks/task-list-query.ts`) is the one place the projection and the `where` live, and `TaskListRow` is *derived* from what it returns so a renamed column fails to type-check at the cards. The route's `kind` parameter speaks the list's own chip vocabulary (`TaskFilter`), and `chipColumns` derives the chip→column mapping from the same maps `taskChip` classifies with rather than restating them. Everything the screen decides — `organizeTasks`, `listState`, `filterOptions` — is a pure selector beside them, tested there rather than in a component
- Live-view transcript (issue #121): `toChatView` (`src/lib/chat/chat-view.ts`) is the pure mapper from stored message rows to the view-model the transcript renders (`user-chip` / `agent-markdown` / `tool-event` / `system-note`); the components are dumb renderers. Agent turns render as GFM markdown via `renderMarkdown` (`src/lib/chat/markdown.ts`) — a self-hosted unified pipeline (no CDN at build or runtime) whose plugin **order is the safety argument**: raw HTML is escaped to literal text, rehype-sanitize's allowlist then covers what markdown itself can produce (`javascript:`/`data:` URLs), and only trusted plugins run after it (highlighting, the recommendation marker), which is why their classes survive. Read that module before touching the order. Syntax colours are fleet CSS variables in `globals.css` — never import a highlighter theme. The tree must resolve **one** `highlight.js` (issue #150): the grammars are imported directly but `rehype-highlight` runs them on the core its own `lowlight` resolves, and a mismatch fails only at render time in the browser — so `package.json` tracks lowlight's range (`~11.11.0`), not the latest 11.x, and `markdown.test.ts` asserts the lockfile has no skew
- Bounded outbound I/O (issue #151): a stalled dependency must never freeze dispatch, the discipline #128 gave the Docker probe. Every outbound call the orchestrator awaits carries a wall-clock bound built on one primitive, `raceWithTimeout` (`src/lib/timeout.ts`), which returns a sentinel so each caller keeps its own policy — the admission probe fails *open* (#115), the agent-container census reports *unknown* (#152), a Discord REST call fails *closed*, a GitHub request additionally aborts its connection. Probe-shaped callers go through `runBoundedProbe` in that same module, which folds a *rejection* into the same three-way outcome because a probe's caller has to decide what a non-answer means whichever way it arrives; it is a thin wrapper over the race and must stay one — a second implementation drifts (the `unref` is the first thing it loses), so the race stays written once. GitHub clients only ever come from `createOctokit` (`src/lib/github/client.ts`), which installs the bound as a `request.fetch` wrapper because @octokit/request has no timeout option; an eslint rule bans `new Octokit(` anywhere else. A Discord call abandoned at the bound is never retried — the attempt may still land, and a retry would double-post
- Queue bookkeeping (issue #151): the poll loop keeps **two** sets, and merging them is what wedged the box on 2026-08-18. `inFlightTasks` is the re-entrancy lock, held until the driving promise settles (`startTask` marks its container idle *before* it commits, pushes and opens the PR, so an earlier release would run two agent execs in one container). `slotReservations` is slot accounting: it stands in for a container being provisioned and is released the moment the container registers or the task turns terminal, never waiting on a promise. `occupiedSlots` additionally ignores any reservation whose task has finished, so the count self-heals within one poll. Nothing, though, makes that count *true* — so the fleet-health watchdog no longer takes it on trust (issue #152). Its three #126 signals all read `occupiedSlots()`, which made a phantom reservation invisible by construction: it held the box's only slot for ~1.5h while the queue refused every pickup and `needsYou` stayed empty, because from the watchdog's view the box was legitimately saturated. The fix is a fourth *observation*, not a fourth mechanism — the sweep asks the daemon what agent containers really exist (`observeAgentContainers`, `src/lib/docker/agent-containers.ts`, which also owns the container-name prefix the census, the admission probe and the reaper all filter on) and hands both numbers to `decideFleetHealth`, where a sustained disagreement becomes the same pickup-wedged card and one-time ping the other three use, carrying its own remedy because a phantom slot lives in orchestrator memory and only a restart clears it. The ping is deduped on the *cause* and re-fires only on an **upgrade** (`dispatch` → `phantom-slot`), never a downgrade: a downgrade means we observed less, not that the fleet recovered, and re-pinging there would demote "restart the app" to "go and look" on a box that still has a phantom. Three rules keep it from crying wolf: the comparison is **one-directional** (`occupied > live` only — more containers than counted slots is the memory-admission probe's business), a **null census is *unknown*, and unknown decides nothing either way** — it may not manufacture a divergence (a zero census reads as "restart the app", so a daemon that cannot answer must say nothing rather than be misread as saying none) and it may not clear one, since only positive agreement stops the clock; erasing on unknown would have meant 40 consecutive answered sweeps to reach the threshold, which a daemon hiccuping once every 20 min never gives, and a hiccuping daemon is the likeliest companion of a real phantom, and only `live` corroborates — a parked container is `docker stop`ped since #93, so it is absent from *both* sides and cancels out, while counting it into the ceiling would instead hide a phantom sitting behind it. Queued work is gathered every sweep rather than only behind a seemingly-free slot, since whether a slot *reads* free is the fact under suspicion. The debounce is its own tunable (`OCCUPANCY_DIVERGED_MINUTES`, default 20 min in `budgets.ts`), far longer than the 3-minute pickup one and set by the worst *honest* case: a task holds its slot from reservation but has no container until `createWorkspaceContainer` returns, and that call runs `ensureImage` inside itself, so a cold agent-image build is legitimately uncorroborated the whole time — and this card's advice is a restart, which would kill exactly that task. The card names the two numbers it judged — what occupancy claims, and what the daemon reports — because the operator's action is a restart, not a wait. The dashboard's `slots.used` stays DB-derived (`occupants.length` via `isLiveTask`) and is deliberately *not* re-derived from the counter: those two surfaces disagreeing is what the #151 incident looked like from outside, so overwriting either with the other would hide the evidence rather than reconcile it — they are reconciled instead by making the *gating* number read the same fact the dashboard does (below), which is what closes the gap without blinding the surface
- Slot bookkeeping never outlives its task (issue #159): the task row, not memory, is the authority. `occupiedSlots` counts neither a reservation nor an `activeTasks` entry whose task the DB calls terminal (`taskIsFinished`, `src/lib/tasks/stored-status.ts` — the one predicate, shared, because a fleet that disagreed with itself about whether a task had finished is how bookkeeping outlived its task twice), and `releaseSpentReservations` then drops what the count skipped. That is a true invariant needing no Docker call: a `completed`/`failed`/`cancelled` task runs no agent process. It is also what makes `slots.used` and `occupiedSlots()` agree in every normal state — both now exclude terminal tasks and parked passes, each pinned by its own test — so a residual disagreement is real evidence rather than an artefact. The prune deliberately leaves containers alone; the stale-container reaper already owns any container whose task is neither live nor run-owned, and removing them here would race it. Beyond that, a **blocked** pickup is re-checked against the daemon every ~30 poll seconds (`reconcileSlotsAgainstDaemon`), fixing the direction the admission probe could never cover: that probe sits behind `slotFree`, so a phantom slot failed the slot test first and it only ever caught *under*-counting, never the over-counting that stops work. Both halves are one-directional and fail-safe, because freeing a slot out from under live work is worse than the wedge it fixes — an entry goes only on a positive 404 (`containerIsAbsent`, which tests *existence*, not liveness: an entry in `setup` is created-but-not-started and a parked pass is `docker stop`ped, and `isContainerRunning` calls both gone), a reservation only once it outlives `PROVISIONING_GRACE_MS` *and* its task still records no container. That grace is deliberately the same 20 min as `OCCUPANCY_DIVERGED_MINUTES` and for the same reason (a cold `ensureImage` build inside `createWorkspaceContainer`), so the watchdog's card never fires before the self-heal it would be warning about
- Orchestrator state a route handler touches lives on `globalThis` (issue #159), via `processSingleton` (`src/lib/process-singleton.ts`). Next compiles `instrumentation.ts` — where the queue loop, the sweep and the Discord bot run — and the app-router route handlers into **separate module graphs**: same process, one registry each, so a module imported from both is *evaluated twice* and its module-level `const` state exists twice. Measured on 16.1.6 against the production entrypoint (`output: standalone`): `turn-manager` loads twice, and `POST /api/tasks/[id]/complete` holds the second copy while the queue counts the first. That is why one normal UI close of an interactive session held the box's only slot until a restart, deterministically, while the same close from Discord always worked — Discord's path is a dynamic import from inside the orchestrator's own graph. `globalThis` is the only registry the two graphs share, so it is the only fix available; a plain module-level value is still right for state one side alone ever sees. The regression test loads `turn-manager` twice through `vi.resetModules()`, the only seam that can see a defect which is not in what either copy does but that there are two. **Still split, and known (needs filing):** `runAutonomySweep` is called from the GitHub webhook route, so a webhook-triggered sweep runs on the app-router graph — where `fleetHealthState`, `sweeping`, `inFlightClaims` and every announce-dedup set are that graph's own, freshly empty. Its consequences are worse than they look: `recordFleetHealth` *is* globalThis-backed, so a webhook sweep computes all-clear signals against an empty debounce clock and overwrites a standing needs-you card; `isQueueRunning()`/`getQueueLastProgress()` read that graph's stopped loop; and two sweeps can run and claim concurrently. Filed, not fixed here — every one of those needs the same treatment and concurrent sweeps need their own tests
- Quota observability (issue #165): the fleet writes down what it does not understand rather than dropping it. `stream-recorder.ts` is a durable, append-only JSONL log **beside the SQLite database** (so it inherits `/data` with no migration) holding every unrecognised stream event verbatim plus every pass's exit condition, because the one thing that cannot report a rate limit is the agent that just hit one — the orchestrator is an ordinary Node process reading stdout, it is not rate-limited, and it does not need to be conscious at the moment of the wall. `rate_limit_event` is recorded despite being recognised and now consumed (#167), and stays recorded after it: the state row #167 keeps is latest-wins and parsed, so this log is the only verbatim history — the only place a window's shape over time, or a field this build does not model, can be recovered from. It is bounded three ways (payload cap, a per-(task, event-type) cap that emits one `suppressed` marker rather than going quiet, rotation to one prior generation — the *oldest* evidence is usually the interesting evidence) and swallows its own errors, because it sits in the stream-parse path of every turn and a log that can break the pass it observes is worse than no log. Three findings from the spike bind the tickets above it: `rate_limit_event` **does** reach stdout under `--output-format stream-json --verbose`, but a rejection then arrives as `subtype: "success"` with `is_error: true` / `terminal_reason: "api_error"` / `api_error_status: 429` — so the only field the orchestrator reads is exactly the one that cannot tell a quota wall from a clean finish, which is why `TurnResult` now carries the terminal event whole; a rejected headless pass **exits in ~2s rather than waiting**, so the pause design detects an exit, not a hang; and the unified-window machinery is **subscription-only** (an API-key lane emits no `rate_limit_event` at all — #172/#173 get no quota telemetry from a metered lane). `scripts/rate-limit-stub.mjs` reproduces any limit state on demand via the `anthropic-ratelimit-unified-*` headers, and its enum values are the ones the binary actually accepts — getting them wrong is silent
- Fleet quota state (issue #167): the CLI's `rate_limit_event` stops being thrown away. The parser reads it into `TurnResult.rateLimit` and writes it, **at the moment of observation rather than at the end of the turn**, to the single `quota_state` row (an interactive turn can run for an hour, and the fleet's freshest fact must not arrive last); the dashboard's quota tile renders that row. Latest wins in both senses — one row per lane (fleet-wide until #175 made it per-lane), and within a turn the *last* event, because the CLI emits one per API attempt and only the newest describes the account now. Three shapes the wire has that the CLI's own schema does not, each pinned by a test against the captured fixtures: `utilization` and `resetsAt` are frequently **absent, not null or zero** (a missing utilization read as 0% would describe a walled account as an idle one — #171's gate inherits this), the event nests its fields under `rate_limit_info`, and it carries `isUsingOverage`/`overageInUse`, which #173 needs and a reader written to the documented list would drop. Enums are held **verbatim as strings, never parsed against a union**: a member a later CLI adds must reach the screen, so an unknown status paints in a tone that claims nothing (`quotaSeverity` -> `unknown`) rather than throwing or being dropped. There is only ever one limit window on the tile because the event carries one — the server picks the *representative claim*, the window closest to tripping — so "which limit is closest" is a field, not a computation. Pausing (#168) is the first thing that acts on any of it; admission (#171) is the other. The row is written in the **wire's own encoding** (the CLI's field names, unix-second resets) and read back through the same `parseRateLimitEvent` the stream goes through, so there is exactly one reader of an observation and no second defensive parser to fall out of step. The tile makes one inference of its own: an observation whose stated reset has since passed goes **quiet**, keeping its words and losing its colour and its bar — a red `rejected` over a wall that lifted hours ago is crying wolf. A row rather than an in-memory store because a five-hour window outlives a deploy, and because the writer (the stream parser, in the orchestrator's module graph) and the reader (the dashboard's route handler, in the app router's) share nothing but the database (#159); a table rather than a column on `settings` because folding an observation written on every API attempt into that row would make the settings screen's "last changed" report the fleet's traffic instead of the operator's last press
- Quota pause (issue #168): a pass the account's quota **refuses** parks its run instead of failing it — before this, a wall spent one of the ticket's three attempts and three of them routed a perfectly good ticket to a human because the account ran out of window. The Claude Code adapter's exit classifier (`classifyClaudeExit`, `src/lib/harness/claude-code/outcome.ts`) takes **both** signals, because each alone lies: the exit condition says the pass ended on an API error but reports `subtype: "success"` at a wall (#165's finding, which is why `TurnResult` carries the terminal event whole), and the `rate_limit_event` says the account was rejected but is emitted per API attempt — a pass can observe a rejection, be retried past it, and still finish, and pausing *that* run would park a finished attempt on a five-hour clock. A rejection carrying **no reset time takes the ordinary path**: a run paused on an unknown window is stranded where no later ticket can find it, so the fleet spends the attempt rather than inventing a clock it does not know the length of. The decision is the reducer's (`pauseRunOnRateLimit`), emitted **ahead of both other readings of a finished pass** — a refused turn never reached the model, so its "final message" is the CLI's own session-limit line (which the blocked-marker detector would read as a question nobody asked) and its empty diff is the wall's, not the work's (which #106's empty-pass path would charge as a strike). The executor writes `runs.status = rate_limited` + `resumeAfter` and **nothing else**: no `finishedAt` (the run has not finished, it is waiting), no attempt, no `interruptionCount` — the two bounds keep measuring what they say. The container is **removed, not stopped** as a blocked run's is: a parked container holds ~2 GiB while holding no slot (2026-08-04), and a five-hour window is far too long to hold one for. The status vocabulary is one leaf module (`src/lib/orchestrator/run-status.ts`) because the two questions it answers pull in opposite directions and both are **inclusion** lists, so a status added later is by default neither: `rate_limited` is *active* (the ticket is still this run's — claiming a second one over it would spend the very attempt the pause protects) and *not reclaimable at boot* (it waits on a clock, not a lost turn, exactly as `gated`/`blocked` wait on a human). On the surfaces it stays under **Running**, labelled paused with its countdown, and deliberately never reaches needs-you — nobody has to *do* anything about a quota window, and that section means a human decision is required; the digest reads the same `paused` field so the two cannot disagree. Deliberately implement-shaped passes only: a walled review pass already fails closed to a human without spending an attempt, and #171 is the ticket that stops a pass starting under a wall at all. Resuming a paused run is #169, below
- Quota resume (issue #169): a paused run **resumes itself** once its window resets, continuing the same conversation rather than starting over. The 30-second sweep is the driver — a paused run is gathered every tick like everything else that waits — and a resume is subtracted from the claimable slots exactly as a queued review is, which is what makes "resuming existing work outranks claiming new work" true when slots are scarce rather than a matter of which action executes first. It is deliberately **not** held by the daily cap, the kill switch or the admission gate (#171): all three gate *pickup*, and a paused run is the middle of an attempt the fleet already started — abandoning it at a window boundary would spend the attempt the pause protected, and refusing to finish work would waste the quota already spent on it, which is the same argument #171's gate makes when it says a parked run still resumes. Losslessness rests on the #165 spike's measurement, which is why the design is this small: for Claude Code **one file** is the whole transcript (`~/.claude/projects/<mangled cwd>/<session id>.jsonl`, derived by the adapter at `claudeTranscriptPath`), a pass killed mid-tool-call resumes knowing how far it got, and the CLI finds a session by **id** rather than by path. What is copied is whatever the pass's adapter names (`sessionArtifactPaths`, issue #217), and `src/lib/quota/session-transcript.ts` names no vendor path: it keeps one directory per **run** beside the SQLite database (inheriting `/data`, so "survives a restart" needs no migration) holding the artefacts verbatim plus a manifest saying which adapter wrote them and where each came from — keyed by run because the run is what pauses, and a resumed pass is a new task row. Every step degrades rather than fails: a transcript that cannot be copied out costs the pause nothing (the pause protects the *attempt*; the conversation is the saving), and a restore that fails falls back to the declared fallback — same branch, prior context lost — because `--resume` against a session the container has never heard of would fail the pass outright. The resume prompt carries the pass's **original brief** behind its preamble for that same reason: it must stand on its own whichever way the restore went, and it tells the pass to read the branch rather than claiming a conversation is above it. Jitter is a **hash of the run id**, not a random draw (`resume-jitter.ts`): the reducer is pure and re-decides every 30s, so a random offset would move between ticks and make a run eligible at 12:01 and not at 12:02. `resumeCount` is bumped when the resume is *decided*, not when the pass starts — a resume whose task never starts would otherwise retry every sweep forever — while the run keeps `rate_limited` and its `resumeAfter` until the pass actually starts, so a restart in between leaves a run that is still visibly paused rather than one pretending to be claimed. Past the bound the ticket goes to a human the way exhaustion does, but the run lands in **`exhausted`, not `failed`**: attempts are counted from failed runs and the pauses spent none, so re-arming later gets the attempts the ticket never used. The bound is checked **before the clock** — a run with no resumes left is never going to resume, so waiting out five hours would only delay telling the human. The **allowance follows the pass, not the row**: a resume is a new task row for the same attempt, and every budget control in the turn manager is scoped to the task, so left alone one attempt's real ceiling would be `(1 + resumes) x run.budgetUsd` — $80 by default, $300 for a ticket carrying a `budget:` directive, and on the one path with no pickup gate in front of it. `tasks.resumedFromTaskId` is what makes the chain a fact, and `resolvePassBudget`/`spendCarriedIntoPass` (`src/lib/orchestrator/pass-budget.ts`) the one place the harness cap, the pre-turn check and the exhaustion judgement all read: a resume of an attempt $18 into $20 gets $2. Lineage rather than the run, because the run also owns review passes with their own allowance and may own two *distinct* repair passes, each entitled to its own — only the chain tells "the same pass, continued" from "another pass of the same kind". Only the **attempt's** budget is netted: a repair pass is never an attempt, so netting its own $5 would hand a resumed repair small change to merge a branch with and a refusal would have to fail an attempt a repair pass may not spend — a bounded residual (its $5 again, at most `MAX_RESUMES_CEILING` times) left to #54's accounting, which already charges repair's fix-up turns against `run.budgetUsd` rather than the $5. A pass whose predecessors spent the whole attempt budget is refused **before its container is provisioned** — defence in depth rather than a live path, since exhaustion is judged ahead of the pause and every link in a chain is therefore strictly under the ceiling
- Tier degrade ladder (issue #170): losing *one tier's* allowance steps the fleet down a tier and carries on, rather than stopping it. The two halves of #164 turn out to be one mechanism — the `rate_limit_event` names the window that refused the pass, and a **tier-scoped** one (`seven_day_opus`, `seven_day_sonnet`) says the account still has quota, just not for that tier, so the run steps `heavy → standard → light` and retries where an **account-wide** one (`five_hour`, `seven_day`, `overage`) can only be waited out. Only account-wide, unreadable, or bottom-of-the-ladder rejections still reach #168's pause. The scope is **derived, not enumerated** (`src/lib/quota/tier-ladder.ts`): the trailing segment of the limit type goes through the same `normalizeModelTier` a ticket's `model:` directive does, so a `seven_day_haiku` a later CLI adds is understood on arrival while `seven_day_overage_included` reads as account-wide — the cautious answer, which is also what an unrecognised window gets, for the reason `rate-limit-event.ts` holds enums verbatim read from the other end. The step is to the first rung strictly **below both** the tier that ran and the tier the window names, because a `seven_day_sonnet` wall seen on a heavy pass would otherwise step straight into the window that just refused. The decision is the reducer's, ahead of the blocked-marker and empty-pass readings for the same reason the pause is; the executor writes `runs.model` (the tier that actually ran, which every later pass of the attempt resolves through) plus `runs.degradedFrom` **once**, on the first step, so a run that walked heavy → light still reads as one that was asked for heavy rather than a standard one that slipped a rung. Two columns, because `model` has to keep meaning what the spend is read against. The retry is a fresh **queued task of the same kind** under the same run carrying the same prompt, branch and PR — so a repair degrades as a repair — and it records the refused pass as the one it continues (`tasks.resumedFromTaskId`, #169's lineage), so the attempt's budget follows the pass down the ladder rather than being handed out again per rung; it deliberately does *not* carry the session, because the pass that continues a conversation is the same pass on the same tier, which is the resume's promise and not this one's — and the run's status is deliberately untouched: an `implementing` run with a queued task is a state the sweep already reads correctly (`implementPassSettled` calls a queued pass unsettled, `hasInFlightRepairTask` sees the queued repair), and boot leaves it alone because it owns live work. The ladder bounds its own retries: `runs.model` only moves downward, so a run degrades at most twice before the next wall pauses it — there is no counter. This is also why the adapter's exit classifier now **reports** a rejection carrying no reset time instead of hiding it: a pause needs a clock and a degrade does not, so what a missing reset means is the reducer's call, and an account-wide reset-less wall still takes the ordinary path and spends the attempt exactly as before. The step is **one-way**: nothing restores `runs.model`, so the rest of the run stays a rung down even past the window's reset — re-testing the wall would cost an agent turn on every later pass; a later attempt is a fresh run and starts at the configured tier. Both endings share `endRefusedPass` in the turn manager, which owns the ordering that is load-bearing in both (container handle taken *before* the terminal write, #159; the replacement pass queued *before* the teardown, so a crash leaves live work rather than a ghost; removal not the blocked run's stop, #93/2026-08-04) and is the only writer of the run patch, so neither ending can quietly spend an attempt. The drain loop that delivers follow-up turns stops on *any* decision but `proceed` rather than on a list of them, which is what a list got wrong the moment this ticket added a fourth. On the surfaces a degraded run stays under **Running** looking like work (mode chip, green phase) with one quiet line naming both tiers — it is working, not waiting — and the digest reads the same `degraded` field so the two cannot disagree

- Quota admission gate (issue #171): the fleet stops *starting* work it cannot finish. `evaluateQuotaGate` (`src/lib/quota/quota-gate.ts`) is the one pure gate two callers share — `decideNext` refuses pickup with it and `buildFleetView` names the hold with it — because a gate computed twice is a gate that eventually disagrees with itself, which is the failure #148 exists to prevent. It holds **new pickup only**: a claim, and the triage pass that is also pickup. Everything already in flight is decided above it and untouched, since refusing to *finish* work would waste the quota already spent on it, and a parked run resuming is that same work continuing. Precedence is stated once in each surface and is the same in both: the kill switch outranks it (a human's hold beats an observation, and naming quota under an engaged switch would point the owner at a wall instead of at the control they hold), it outranks the slot check (a full box empties by itself in minutes; a spent window does not), and on the dashboard the daily cap outranks it (of the two self-lifting ceilings, the cap's is the one a human chose). Three rules make it safe to close a gate on telemetry the fleet does not control: **no observation is not a closed gate** (an API-key lane emits no `rate_limit_event` at all — #165's finding 6, re-confirmed against OpenRouter — and silence the fleet cannot break must not read as a wall; #175 is what makes that rule *reachable*, since the gate reads the primary lane's row rather than the fleet's, so a metered lane is not held behind the subscription's wall), **an absent utilization is not 0%** (#167's rule, inherited verbatim), and **a spent observation stops gating** — load-bearing rather than tidiness, because only a pass making an API call produces a fresh observation, so a gate held by a stale rejection would suppress the very traffic that would lift it; an observation expires at its stated reset, or at `QUOTA_OBSERVATION_STALE_MS` when it stated none, and reopening is self-correcting (the next pass re-observes the wall in seconds). Only `rejected` gates on status: a member a later CLI adds reads as itself and decides nothing, so the fleet is never stopped by a word this build has not heard. The Discord ping fires from *past* the eligibility filter, which is what makes it mean "the fleet is stalled on quota with N tickets armed" rather than "a run paused"; its once-per-transition flag is cleared from the **gate**, not from whether a pause was emitted, because the reducer only pauses when there is work to hold and clearing on "no pause" would re-arm the ping every time the backlog emptied under a standing wall. A single threshold with **no headroom reserved for the owner** — the fleet and the owner's sessions draw on one pool — settable in the UI (`Settings → Quota`), falling through to `QUOTA_PICKUP_THRESHOLD_PERCENT` and then to the built-in default
- The **minimum lane** per pass kind (issue #176) follows the lane field's shape too — same registry (the allowlist, and so the mechanism deciding what is settable), same runtime-catalog vocabulary through `SettingsContext`, same refuse-by-name — with its own resolver and view (`resolveMinLane` -> `MinLaneFieldView`) and its own panel under **Execution lane**, beneath the choice it restricts. Four fields, one per kind, because that is the whole control: triage and review read the work rather than doing it and are free to run on the cheapest lane declared, while an implement pass on a hard ticket may be floored at a capable one; `repair` reads the implement field for the reason it reads implement's tier. It resolves through **two** layers where the threshold and the resume bound have three: "no floor" is a perfectly good answer and is what a fresh deployment means, so an unset override falling through to an unset `AGENT_MIN_LANE` resolves to null rather than to a built-in default — a floor is a restriction, and inventing one nobody asked for would quietly stop the fleet using a lane it was given. One environment variable rather than four, because a floor is a statement about what the deployment will tolerate at all and the per-kind refinement is the screen's job
- The quota threshold as a setting (issue #171) follows the lane field's shape, not the tiers': it shares `SETTINGS_FIELDS` — which is the allowlist, and so the mechanism deciding what is settable at all — but has its own resolver and its own view (`resolveQuotaThreshold` -> `QuotaThresholdView`) and its own panel, because asking a percentage "what tier is in force?" is not a meaningful question. It resolves through **three** layers where a tier has two: a tier may resolve to "pass no `--model` and let the harness decide", but a gate needs a number, so an unset override *and* an unset variable both land on the built-in default. The environment is read through the same `normalize` an override is — a typo is refused there too, never clamped — but is still *shown* verbatim, because a refused value collapsed to "unset" would read back on the screen as a variable nobody had set. Its control is a fixed set of chips rather than a free number: the spread offered is finer than the decision it feeds, a value outside it is refused *with the list*, and the row keeps the one-press `environment` way back. It joins the other panels' single client state even though it is independent of them, because one PATCH returns the whole resolved settings state and a separately-fetched panel would be left showing a row that is no longer the row
- Third-party lanes, proven (issue #175): #164 justified one harness adapter on the grounds that the open-weights field exposes Anthropic-compatible endpoints, and that assumption survived contact with a real one — OpenRouter's Anthropic skin at `https://openrouter.ai/api` answers the Claude Code harness with tool use, extended thinking, `--resume` and prompt caching all intact, with **no provider branching anywhere in the adapter seam**. Two things under it did not survive, and both are now mechanisms rather than hopes. **Cost:** the CLI's `total_cost_usd` is Anthropic list prices applied to whatever model it was handed, so it billed a turn on a *free* model $0.194985 at $5/$25 per Mtok (`costBasis: "unknown"`, where a first-party model reads `"list"`) — 16.7x the paid slug and infinitely over the free one. So a lane may declare `prices` per tier and `lane-cost.ts` charges every budget from them (`chargeForTurn`, applied once in `runTurn` so no caller reads two figures); a lane with none — Anthropic-direct, where the CLI is right — keeps the harness's number, and a turn that reported no tokens keeps it too, knowingly, because over-reporting stops work early while under-reporting spends money nobody authorised. Prices are **all three tiers or none**, since a lane priced for `standard` but not `light` would fall silently back to the fiction the moment #170's ladder stepped down. Token counts come from `modelUsage`, never the sibling `usage`: the two disagree (`usage.input_tokens: 10` beside `modelUsage.inputTokens: 909` on one measured turn) and only `modelUsage` reproduces the CLI's own figure at list prices to the cent, so it is the aggregate and `usage` is the last API iteration. The four captured `result` events are checked in (`lane-cost-fixture.ndjson`) because the ticket's claims are claims about specific observations. One consequence lives in the adapter: a lane with prices is passed **no `--max-budget-usd`**, because the CLI enforces that flag against its own figure, so a $20 ceiling would stop a turn at ~$0.30 of real spend — mid-work, and invisibly, since a budget stop is not `error_max_turns` and the pass would be parked as finished. Its cost, named: a review or triage pass has **no in-turn ceiling** on a priced lane, since their $5/$2 budgets reached the harness through that flag and nowhere else — but enforced against the CLI's figure those ceilings cut a review off at ~$0.08 of real spend, mid-work and invisibly, so the trade is a bounded overspend against a silently half-read PR; `--max-turns` and the daily cap (which counts every autonomous pass kind, now at real prices) are what remain. That decision reads the lane *definition* (`declaresPrices`), never the pass's resolved tier: "does the CLI price this provider?" is true of the endpoint before any tier resolves, and keying it on the per-tier `prices` would restore the ceiling in exactly the case nobody is watching. The tier itself has one lane-specific rule for the same reason: **a priced lane resolves an unset tier to `standard`** rather than to "pass no `--model`". On Anthropic-direct that fallback still means what it always did, but on a lane with its own model map the harness's own default is an identifier from *another* provider's catalogue — the endpoint may refuse it, or serve a Claude model at a price the lane's table does not hold, and the fleet would charge the fiction for it. Unset is not an edge there; it is what one press of the settings chip leaves behind. **Quota:** the unified-window machinery is subscription-only, re-confirmed against a second provider — no `anthropic-ratelimit-*` response header, no `rate_limit_event` on a full harness turn — so `quota_state` is keyed by **lane id**, and `createOutputHandler` takes the lane (the third adapter member to, for the reason the other two do). Under one fleet-wide row the subscription's last reading would have stood in as the current state of a lane that cannot produce one, which is exactly how a lane bounded by spend gets gated by somebody else's wall; The sweep therefore feeds the gate (#171) the *primary lane's* observation via `primaryLaneOf` — the same single resolution #174's money guards read, shared with the dashboard, so the lane whose quota is judged, the lane whose spend is capped and the lane named on the screen can never be three different lanes; the gate's own "no observation is not a closed gate" rule then does the rest, which is why per-lane keying is the whole fix rather than a new branch in it. The tile therefore distinguishes a lane that can never report from one that merely has not yet — one is permanent and by design, the other is pending, and an operator told the wrong one waits for a reading that will never come (since #219 that distinction is keyed on the harness's declared telemetry capability, as **"cannot report"** against **"nothing observed yet"**, with a metered lane's "bounded by spend" kept as a note under the latter). Caching *does* work through the skin (a cached turn's input fell from 21261 to 210 tokens, 8.8x cheaper) but cache **writes** are never reported (`null`, not a count): they arrive as ordinary input tokens, which is why an absent `cache_read`/`cache_write` price is charged at the input rate rather than at zero. `scripts/openrouter-lane-check.mjs` re-answers all of it on demand, harness-free so a surprising result points at the endpoint or the harness rather than at both

## Database

Schema at `src/db/schema.ts`. Seven tables: `projects`, `tasks`, `messages`, `runs`, `settings`, `quota_state` (one row per execution lane, keyed by lane id since issue #175), `metered_spend`.

- `runs` is the Phase 5 autonomy ledger — one row per attempt at one ticket; a run owns one or more tasks (its implement pass plus any review passes). Interactive tasks have no run, which exempts them from the daily autonomous spend cap by construction (`src/lib/orchestrator/spend.ts`)
- Who paid (issue #174): `runs.lane`/`runs.laneBilling` and `tasks.lane`/`tasks.laneBilling` record the execution lane a pass ran on and its billing kind, written at pass start (a follow-up turn re-records, so each turn's dollars are booked to the lane that actually spent them). The billing kind is stored rather than looked up, because `lanes.yaml` changes under a deployment and a retired lane would otherwise rewrite the billing history of every past run. `metered_spend` is the real-money ledger, one row per local day: a **ledger** and not a sum over tasks because a task's `totalCostUsd` is a running total carrying no day — a chat session opened Monday and driven all week has one figure, and attributing it by creation or last-update either under-counts (spending past the cap) or double-counts (holding the fleet over money it did not spend today), while the *increment* at the moment a turn's cost lands is unambiguous. `updateTask` is the one funnel every task-cost write goes through, which is why the booking lives there and not at its call sites. `settings.meteredSpendConfirmedAt` is the confirm-once gate's one durable fact
- Budgets (issue #18): `MAX_BUDGET_USD` is the **$20 per-attempt** default — it was $5 per *task* before Phase 5, and interactive tasks deliberately inherit the new, more generous default. A ticket's `budget:` directive (Workflow section) may raise one attempt to at most $75; review passes carry their own ~$5; the $500/day autonomous cap and all ceilings live in `src/lib/orchestrator/autonomy/budgets.ts`
- `runs.status = rate_limited` + `runs.resumeAfter` is the quota pause (issue #168): non-terminal, set at pass completion when the account refused the pass, and cleared when the resumed pass starts (issue #169) — the sweep queues the resume but leaves both alone, so a restart in between finds a run that is still visibly paused. It is the only status that waits on a clock rather than on a human or a turn. `runs.resumeCount` bounds it: its own counter, because a pause spends neither an attempt nor an interruption and bumping either would change what those numbers mean. It bounds a **lane move** too (issue #176) — a move is a continuation of the same attempt exactly as a resume is, so it answers to the same number rather than getting a second one to keep true A pass refused on a *tier-scoped* window never reaches it (issue #170) — it degrades instead
- `runs.degradedFrom` is the tier degrade ladder's ledger entry (issue #170): the tier the run was **asked** for, written once on the first step down and never rewritten, null on a run still running at the tier it was given. `runs.model` keeps meaning the tier that **actually ran** — it is what the spend is read against and what every later pass of the attempt resolves through — which is why the requested tier needs a column of its own rather than overwriting it
- `runs.declaredTier` is the tier the ticket's Workflow section declared, as parsed at claim (issue #198), null when it declared none — written once at claim and never rewritten, where `runs.model` is rewritten by the implement pass with the tier it resolved. It exists only so tier coverage can tell a declaration from a default; which tier ran stays `model`'s to say
- `runs.reviewResult` holds a finished review pass's parsed verdict until the orchestrator has acted on it; `runs.reviewVerdict` is the last verdict actually posted to GitHub, and `runs.reviewedHeadSha` the commit that verdict was written about (issue #131). A parked run whose PR head has moved past it — a human's *Update branch*, commit or `main` merge — is disarmed, has its stale review dismissed, and re-gates + re-reviews once; past the review-cycle budget it goes to a human instead
- `tasks.kind` distinguishes interactive (default) / implement / review / triage; `tasks.runId` links a task to its run; `tasks.tier` records the model tier a pass ran at, beside the lane it ran on (issue #173) — the pair is what makes an interactive session's real-money cost interpretable, and interactive work is the only kind that crosses onto a paid lane; `tasks.resumedFromTaskId` links a pass continued past a quota wall to the one it continues — a resume off a pause (issue #169), a retry a tier lower (issue #170) or a retry on another lane (issue #176) — the lineage the attempt's *budget* follows, so a continued pass spends what its allowance has left rather than the whole allowance again; `tasks.triageResult` holds a finished triage pass's parsed exit until the sweep applies it (triage owns no run, so its spend is counted into the daily cap by kind in `spend.ts`)
- `projects` carries `autonomyEnabled` (default off) plus cached `preflightStatus`/`preflightReason`
- `settings` is a single durable row (id `fleet`) of operator state flipped at runtime, as opposed to env config in `src/lib/config.ts` which is fixed at boot. It holds `globalAutonomyPaused` — the global kill switch (issue #118), read fresh by the sweep each tick (via `src/lib/settings.ts`) and toggled by `PATCH /api/settings/autonomy`. Engaged, `decideNext` emits no pickup actions at all (no claim, no triage pass) and nothing else changes: in-flight runs, gating, review and exhaust routing carry on, exactly as under the daily-cap pause whose gate it shares. `AUTONOMY_ENABLED` stays the **boot master** (false = sweeps never start); the flag is the runtime pause layered on top, so it takes effect at the next tick with no restart — and, being a row, an engaged switch survives a restart. Both observability surfaces read the row, never the sweep's log line (which only fires on a tick that had a ticket to claim): the dashboard's dot reads `held` with its banner, and the daily digest leads with an **Autonomous pickup** section (issue #143) stating the hold as it stands when the digest is written — the flag has no history, so a switch lifted before the morning send leaves the covered day reading quiet. Both read one field, `FleetView.pickupPaused` (issue #148), which carries every fleet-wide reason so the surfaces cannot disagree: `autonomy-off-at-boot` (dot `off`) outranks `kill-switch` (dot `held`) outranks `daily-cap`, then issue #174's two money holds `metered-cap` and `metered-unconfirmed`, then #171's `quota-gate` (dot `paused` for all four) — the master leads because lifting the switch under it would change nothing. Per-project holds are deliberately not in that field (one repo failing preflight is not a held fleet): they ride `ProjectPickupHold` on the backlog rows and the per-project preflight card, both fail-closed exactly as `decideNext` is
- UI-editable settings (issue #166): the `settings` row's second job. `overrides` is a sparse JSON object of env-config fields a human may change while the fleet runs, merged over the environment by a **pure resolver** (`src/lib/settings-resolver.ts`) — one JSON column rather than a column per setting, so a later ticket in #164's quota work adds a field to the registry there and not a migration, and a retired key is dropped on read instead of left as a dead column. Four rules, each pinned by a test: an **unset** field falls through to its own environment default (so a fresh deployment behaves exactly as before, and a cheap triage default never quietly decides what the reviewer runs on); a **set** one wins and reports its **provenance**, which is what makes a surprising tier debuggable from the screen; only keys in `SETTINGS_FIELDS` are settable at all, which is how "a UI override may never widen a hard ceiling" is enforced — the ceilings are refused *by name* (`FIXED_CEILINGS`) rather than absent by oversight; and a disallowed value is **rejected with a message, never clamped**, because a clamp turns "I asked for X" into "the fleet quietly did Y". The quota **resume bound** (issue #169) follows the threshold field's shape exactly — its own resolver, its own view (`resolveResumeBound` -> `ResumeBoundView`), its own panel under the same **Quota** section, and the same three layers ending in a built-in default, because a bound needs a number too. It is a *count* rather than an enum, held to exactly the vocabulary the screen offers — one ceiling derives both the chips and what the route accepts, so a press can never be refused — and validated for digits before conversion, because `""` converts to `0` and reading a blank field as "never resume" is the quiet reinterpretation this layer exists to refuse. The freshness rule lives at the call sites, not in the resolver: `getConfig()` memoises into a module-level value on first read, so an override cannot ride on it — `getSettingsOverrides()` is re-read at the point of use (the turn manager, per pass and per follow-up turn), which is what makes a change take effect at the next sweep with no restart
- Model choice is a **tier**, not a model id (issue #166): `heavy` / `standard` / `light` (`src/lib/model-tiers.ts`), with `opus` / `sonnet` / `haiku` kept working as aliases so a ticket carrying a `model:` directive doesn't break. The vocabulary is one module because three surfaces speak it — the settings UI, the env defaults and the semi-trusted ticket directive (which the parser now normalises to a tier, so everything downstream deals in tiers only) — and `TIER_MODEL_IDS` is the pre-lane tier→id map, which execution lanes (#172) now supersede per lane — it survives as the default for a caller with no lane in hand. Precedence, ordered once in `resolveAgentModelChoice`: a ticket's directive (work-carrying kinds only — the ticket chooses the model its *work* runs on, not the reviewer's) beats the UI override beats the environment. An env value that names no tier (a pinned `claude-opus-4-8`) stays legal and passes through verbatim; the UI, whose job is the durable choice, takes tiers only
- Execution lanes (issue #172): which harness runs a pass, against which provider, on which model is **configuration**, not code. A lane is `{ adapter, auth env var names, base URL, tier→model map, caps, billing kind }`, declared in the checked-in `lanes.yaml` at the repo root (`src/lib/lanes/lane-config.ts` parses it; the production image must `COPY` the file, as Next's standalone output carries only what the bundle imports). **Secrets appear only as variable names**: `auth` maps the variable the *harness* reads to the orchestrator variable holding the secret (Claude Code reads `ANTHROPIC_AUTH_TOKEN`, the OpenRouter key is provisioned as `OPENROUTER_API_KEY`, hence a mapping and not a list), and the parser enforces `^[A-Z][A-Z0-9_]*$` on both sides, so an inlined credential is a parse error rather than a secret in git. No lane **secret** is ever stored in the DB or served by an API route — the settings row holds the chosen lane's *id*, `runs.lane` holds the id a run used, and the settings payload carries variable *names* only; the rule a project route once broke by serving a stored token in cleartext. Resolution (`src/lib/lanes/resolve.ts`) is pure — `(catalog, pass kind, config, overrides, env)` in, `{auth values, base URL, model id, caps}` out — and it **reports rather than falls back**: an unavailable lane refuses *before* a container is provisioned, naming the missing variables, which replaces a live agent dying inside the harness with "Not logged in". Only the *unset* default walks the file's `primary` preference order (subscription first, then the API key — exactly what `config.ts` did before lanes, now written where a human can read it); an explicit choice, from the settings screen or `AGENT_LANE`, is honoured even when it is broken, because routing around an operator's choice is how a fleet spends money nobody authorised. The tier→id map moving into the lane is why `resolveAgentModel` became `resolveAgentModelChoice`, stopping at the tier: the tier is the durable human choice, and what it *means* now belongs to the endpoint being called
- The harness adapter seam (issues #172, #214) is `src/lib/harness/`. #172 drew it at `buildExecEnv`, `buildCommand`, `createOutputHandler`, chosen because those three were already pure and already tested; #214 widened it to what a second harness actually needs, as an expand step that changes nothing on the Claude lane (same command, same environment, same pause/degrade/failover decisions). An adapter now also declares its `image`, its static `capabilities` (`userInvokedSkills`, `quotaTelemetry`, `reportsCost`, `sessionResume`), `composeSkillInvocation(skill, agenda)`, `sessionArtifactPaths(sessionId, cwd)` and `mapEffort(level)` (null = no equivalent, so the flag is omitted rather than guessed at), and its `TurnResult` (`turn-result.ts`) carries a **normalised outcome** — `completed | turn-limit | refused { kind: quota | auth | other, resumeAfter, limitType } | failed` — beside the vendor's verbatim `terminalResult`, which stays only for the stream recorder. **The turn manager and the reducer branch on the outcome and nothing else**: attempt exhaustion is `outcome.kind === "turn-limit"`, the wall ordering (degrade, failover, pause) reads `refused { quota }` and only that, and the review-verdict and triage-exit readers (`pass-output.ts`) take the `TurnResult` rather than re-parsing a stream — no module outside `src/lib/harness/claude-code/` reads the CLI's result subtype, error flag or HTTP status. A **null** outcome is deliberately not a fifth kind: it is the harness never having said how the turn ended (a container death), which the interruption bound owns (#97), where a `failed` outcome is the work's. A non-quota refusal and a `failed` outcome take the ordinary path exactly as they did before the vocabulary existed; what an `auth` refusal should do is #220's. The Claude Code adapter is a directory: `claude-code/index.ts` (the adapter — effort maps one to one because the fleet's five levels *are* the CLI's `--effort` enum, the skill invocation is byte-identical to the seed composer's slash line, the artefact path is the one transcript file), `stream-parser.ts` (the parser; the orchestrator does not import it — the `finalMessage` it reports is `readFinalMessage`'s one rule: the result event's own `result` string, which is what the exit readers read, falling back to the last assistant text block, which is what the blocked-marker detector read; the two are pinned identical on every captured stream), `outcome.ts` (`classifyClaudeExit` and `readFinalMessage`: the turn ceiling first, as exhaustion was always judged ahead of the pause; then a refusal only when the **one** API-error predicate holds — `is_error` beside a 429 or an `api_error` reason — read as `quota` when the last `rate_limit_event` says `rejected`, `auth` on 401/403, `other` otherwise; any other terminal error as `failed` naming the subtype) and `image.ts` (a leaf the image builder reads, so the image it builds and the one the adapter names cannot differ; one image per adapter is #216). **The static descriptor table** (`descriptors.ts`: id + capabilities, a leaf with no imports) is what the pure lane parser checks adapter ids against — `parseLaneConfig(text, descriptors = HARNESS_ADAPTER_DESCRIPTORS)`, which is why `LaneAdapterId` is a validated string rather than the table's literal union — and `descriptors.test.ts` pins the table to the registry, so an adapter cannot be registered without a descriptor or described without being registered; `registry.ts` types its production table `Record<HarnessAdapterId, …>` so the first half is a compile error too. **A fake adapter** (`src/test/fake-harness.ts`, registered only under test through `registerHarnessAdapter`, never described in the production table so `lanes.yaml` can never name it) emits scripted normalised outcomes; `fake-harness-turn.test.ts` drives the real `startTask` through it over a real DB and a one-lane catalog — completion, `refused { quota }` reaching the reducer as a pause or a degrade, turn-limit exhausting the attempt, a null outcome interrupting — and is the double every later multi-harness ticket builds on. Recorded Claude streams reach the exit readers' tests through `src/test/claude-stream-fixture.ts`, which asks the adapter's own classifier and final-message rule, so test code does not read the vendor shape either. `container-manager.ts` is harness-agnostic below the seam — `execAgentTurn` runs whatever command and environment the adapter built. Two security facts carry forward and are pinned by tests: no model-provider credential is in the **persistent** container environment (`ANTHROPIC_API_KEY` used to be, and is not any more — the `anthropic-api` lane supplies it per exec), and `ghToken` stays null for every autonomous pass kind. **Session artefacts belong to the adapter (issue #217):** `sessionArtifactPaths(sessionId, cwd)` names the container paths that hold a session's replayable state, and the store (`src/lib/quota/session-transcript.ts`) copies exactly those out at a pause, all or none, and names no vendor path itself — one directory per run holding the artefacts verbatim plus a manifest (adapter, session id, the path each came from); an adapter declaring `sessionResume: false` has nothing copied out, because nothing could ever be put back. Whether the conversation *crosses* is decided as the resumed pass starts, at `restoreSessionTranscript` — the one seam that knows both ends: the pass it continues (`tasks.resumedFromTaskId` → that row's `lane` → its adapter) and the lane it is starting on, resolved a moment earlier (the target a move names is advisory, so the adapter is not known until then) — through the pure `decideSessionCarry` (`src/lib/harness/session-carry.ts`, a leaf). Same adapter: the artefacts go back to their recorded paths and the harness resumes by id, exactly as before. Different adapter, a harness that cannot resume, or a predecessor lane the file no longer declares: the pass starts again on the branch with the work already pushed, its `sessionId` is cleared so the row stops naming a conversation it is not in, and a system note on its feed names both lanes and why. The lane ranking is unchanged — a cross-adapter lane is a legal failover target; it costs the conversation, not the attempt. A continuation queued with no session (a degrade, or a pause whose copy failed) says nothing there, since that was already said on the refused pass's feed and the issue. `cross-adapter-session.test.ts` drives all of it through the real `startTask` over a real database, a real on-disk store and fake lanes on three fake adapters (`FAKE_OTHER_HARNESS_ID`, `FAKE_NO_RESUME_HARNESS_ID` beside the first). The store's pre-#217 one-file `.jsonl` entries are pruned at boot as stale, so a run paused across the deploy of #217 resumes without its context — the declared fallback, not a failure
- Lane-file rules follow the adapter's **declared capabilities** (issue #219), and each lane says which harness runs it. The parser is handed the descriptor table and a parsed lane *carries* its adapter's capabilities (`LaneDefinition.capabilities`, on through `ResolvedLane` and `LaneView`), so no reader downstream looks an adapter up — and a test's lane on the fake adapter carries the fake's capabilities as naturally as a shipped lane carries Claude Code's. One rule is enforced at parse: a **metered** lane on an adapter that does not `reportsCost` must declare `prices` for all three tiers or the whole file is refused naming the adapter and the rule (#175's convention, now a capability check — keyed on the capability, never on billing or the endpoint, so the shipped Anthropic-direct lanes keep taking the CLI's own figure); a **subscription** lane on the same adapter may omit them, since its marginal cash cost is zero and nothing books to metered spend. An unregistered adapter is refused listing the registered ids. Quota telemetry follows `quotaTelemetry`: `readMoneyGuards` — the one quota read the sweep, the dashboard and the settings route share — reads a lane's `quota_state` row only where its harness declares telemetry (`laneReportsQuota`), so the admission gate, the overage check and the tile all see null for a lane that cannot have written one (a row left when a deploy moved the id onto another adapter, or written in breach of a descriptor); the ranking's per-lane map is filtered the same way (`actionableObservations`); and the tier ladder reads only the *refusal's own* window (the adapter's normalised reading of the refused turn), never a stored row, so no observation from such a lane can step it — while a refusal that names a tier still degrades on any harness, which is the spec's "refusals still arrive" and what #214's fake-harness turn test pins. The quota tile therefore keys **"cannot report"** on the harness capability, whatever the billing kind (a Codex subscription lane is subscription-billed and still cannot report), and says **"nothing observed yet"** for a lane that could report and has not — adding "bounded by spend" on a metered one, because that is a fact about the provider, which the tile does not vouch for. The execution-lane settings screen shows, per lane, the harness, whether its agent image is built and whether its credentials are present: image state comes from `readHarnessImageStates` (`src/lib/harness/image-state.ts`), one bounded probe per adapter the file names (`probeImageBuilt`, which tells a positive 404 from a daemon that did not answer — the latter renders *unknown*, never "not built"), and the payload still carries variable names only
- Money guards key off a lane's **billing kind** (issue #174), never off whether a pass overflowed. The cheapest configuration of this platform is not "subscription primary, metered overflow" — it is metered-**primary**, and a guard hung off the overflow transition would let exactly that configuration spend real money on every turn, unconfirmed, uncapped and absent from the dashboard's split. So a metered lane is guarded whether it is primary, an overflow target (#173) or reached by failover (#176), and autonomous work on a metered primary is **allowed** — bounded by a cash cap rather than exempted from one. Two guards, one pure module (`src/lib/lanes/money.ts`), evaluated by the reducer *and* the read model over the same facts so the sweep and the tile cannot disagree: a **confirm-once-per-local-day** press at fleet level (nobody is at the keyboard when an autonomous pass crosses into billing — #173 keeps the at-the-keyboard UX for interactive overflow), and a **real-money daily cap** that is the *lower* of the operator's dial (`METERED_DAILY_CAP_USD`, overridable from the settings screen up to a code ceiling refused by name) and the lane's own declared `caps.daily_budget_usd`, so neither can widen the other and which one binds is reported. The cap pauses through the reducer's **existing** `daily-cap` reason with a detail naming which cap — two caps, one mechanism — while the confirmation gets its own reason, because the cap lifts itself at midnight and the confirmation waits for a press, and on a capped day the cap wins (confirming would start nothing). The two sit on opposite sides of the kill switch in `decideNext` for that same reason: the cap goes above it, where the daily cap is, because its announcement is news either way, and the confirmation goes below it, where #171's quota gate is, because a request for a press must not be made under a hold a human has engaged. Real money is counted in a per-day **ledger** (`metered_spend`), written as each turn's cost lands and only for a pass whose recorded lane bills per token: nothing is exempt by kind, because a chat session on a metered lane charges the same card an implement pass does — the opposite rule from `todayAutonomousSpendUsd`, deliberately, since that cap measures quota-funded autonomy and this one measures cash. What the guards **hold** is narrower than what they count: new autonomous pickup (a claim, a triage pass) and — since #173 layered the attended UX on the same gate — an interactive session's crossing onto a paid lane, but never an in-flight run or a run's follow-up turn. The three impure readers (sweep, read model, settings route) go through one `readMoneyGuards`, so "which lane, at what cap" has one answer. The two figures overlap by construction and must never be added; the dashboard, the digest and the needs-you cards keep them apart. The confirmation is a `settings` column and not a boolean, so nothing has to run at local midnight to clear it

- Interactive overflow (issue #173): when the subscription window **refuses** a pass, autonomous work pauses (#168) and attended work **crosses onto a paid lane** — a human is sitting there waiting, and the asymmetry is the whole ticket. `src/lib/lanes/overflow.ts` is the pure decision (`decideLaneCrossing`) three surfaces share, for the #148 reason: the turn manager routes a pass with it, the queue loop declines to start one with it, and the task screen offers the confirmation from it, so none of them can hold a session the others think is fine. It owns nothing #174 owns — the cap, the confirm-once gate and cap-outranks-confirmation are evaluated through that ticket's own `evaluateMeteredSpend`, because a second copy of "may the fleet spend cash?" is a second answer waiting to disagree with the dashboard. **An active overage is a paid lane**: `overagePaysNow` counts a request that drew on overage, *and* a refused window whose overage window is still serving (the `overage-active` stub scenario: `status: rejected`, `overage-status: allowed`, HTTP 200 — the wall is up, the request succeeded, the card paid), because without that rule an overage-enabled account would never show a `rejected` at all and the wall would silently become a bill. It deliberately does **not** count `overageInUse` alone — the real captured event from a healthy account carries it with `status: allowed` and `isUsingOverage: false`, so reading it as cash would hold the fleet for a confirmation nobody owed. That reclassification enters through `readMoneyGuards`, which now reports the **effective** billing kind, so the sweep, the tile and the crossing all see it without a fourth mechanism — and which, after #175 keyed `quota_state` by lane, also *owns the quota read*: which row to read depends on the lane it resolves, so handing an observation in from outside would have made each caller pick the lane, which is the divergence per-lane keying exists to prevent. Its `quota` is handed back, so the admission gate and the crossing judge one instant of one row; the lane row still declares what it is, which is why every surface names "an active overage on X" rather than accusing a subscription lane of billing per token. An unavailable lane is **not** a wall — a missing credential is #172's report, and routing around an operator's explicit choice is what that ticket exists to refuse; a wall is different in kind, because the choice is intact and simply cannot serve the request. The overflow target is the first **available metered** lane in the file's own `primary` preference order (Anthropic direct before a third party, in the shipped file), so which card gets charged stays a reviewed, version-controlled decision. The guard keys off billing kind rather than off having overflowed, exactly as #174's do, so a **metered primary** asks for the same press on its first interactive turn of the day — #174 deliberately left interactive dispatch ungated and this is the ticket that gates it. A refused session is left **`queued`, never failed**: a press is a press away and the cap lifts itself at midnight. Which is why the crossing is read *outside* `startTask`'s failure boundary and answered by `crossingHoldsPass` — everything inside that `try` fails the task by design (#172's unavailable lane must), and the manual run route reaches `startTask` without passing the queue's check at all. Which is why the pickup loop **steps over the whole interactive kind** while the guards refuse it (`nextQueuedTask(skipInteractive)`) — interactive work sorts first (#15), so one held session at the head of the queue would stop the review passes and resumes behind it, holding up work already paid for with work not yet authorised. On a follow-up turn nothing new was needed: `laneForFollowUp` already resolved the lane *before* dequeuing the message, so the owner's turn is not burnt, the reason lands on the feed once (`noteOnceOnFeed`), and the turn runs on the poll after the press. The crossing *notice* is announced on a change of payer (`payerChanged`) rather than by that text dedup alone, because the sentence quotes the day's running spend — an exact-text comparison would post a new line every turn, a few cents apart — and the pair it compares is the one the ledger reads, so what is announced and what is charged cannot part company. `tasks.tier` joins `tasks.lane`/`laneBilling` for the ledger's sake: a run row has carried lane + tier since #172, and interactive work — the only kind that crosses — has no run row, so without it the one figure the fleet could not account for was the one it spent real money on

- Cross-lane cost routing (issue #176): which lane a pass runs on stops being a fixed setting and becomes **the cheapest lane that can serve it**. `lane-selection.ts` is the one pure ranking three surfaces share for the #148 reason — the crossing routes a pass with it, the reducer decides a failover with it, and the settings screen shows what it would pick, so the row that says "an implement pass will run on X" is reading the answer the pass gets. Two orderings come out of one price table because cost and capability are different axes and only one is what the fleet pays: **cost** is the marginal cash rate (a subscription is *zero* — its quota is already bought, which is why routing is a no-op in the shipped configuration until a wall; a priced lane its own blended rate; a lane billing per token with **no** declared prices is *unread* and therefore ranked last, the cautious answer `lane-cost.ts` argues for, and an active overage moves a subscription lane into that class too since the card is being charged at a rate nothing writes down), while **capability** is a proxy — what the provider charges for what the lane runs, with an unpriced lane at the *top* because it is Anthropic-direct running first-party Claude. That second axis exists only to give a pass kind's **minimum lane** a meaning: a floor is inclusive and admits everything at or above the named lane, so a floor of `openrouter` still allows the (free, first-party) subscription and a floor of `anthropic-api` reads as "first-party Claude only". Ties break on the file's own `primary` order — #173's reviewed overflow ranking, surviving as the tie-break rather than the rule, which is why an overflow now prefers a *priced* third-party lane over the Anthropic-direct one that charges the same. The rate is a **ranking key, not a forecast**: `RANKING_PASS_USAGE` is a stated 1M-token mix (cache-read dominant, off #175's captured turns) priced through the same `priceTokens` the ledger charges from, and nothing here is ever booked against a budget. Three things routing may **not** do: move work off a lane that is merely *unavailable* (a missing credential is #172's report, and papering over a misconfiguration by spending at another provider is what that ticket refuses — so the pass stays where it was sent and dies naming the variable), override a **pin** (an explicit `primaryLane`/`AGENT_LANE` choice turns the ranking off, which is the escape hatch and deliberately *not* a new setting — #172 already distinguishes a decision from the unset default that walked the preference order) *while the pinned lane can serve the request*: a **wall releases the pin**, because #173 crossed an attended session off a walled lane whether or not it was pinned and that has to keep being true — a pin says "do not choose for me" where a wall says the chosen lane cannot serve the request at all, the same difference-in-kind `laneIsWalled` draws against a merely unavailable lane. On the failover path the release is decided from the *turn's own rejection* (`planLaneFailover` drops a pin naming its `fromLaneId`) rather than from the recorded observation, because the fresher fact is already in hand and relying on the timing of a second reading is how a pinned fleet would silently lose its failover, or spend cash the fleet is not permitted: #174's cap and confirm-once press are evaluated **inside** the ranking, per lane against that lane's own declared cap, so a money-held lane is simply not a candidate — and, load-bearingly, the *fall-back* goes through the same evaluation, because when the ranking picks nothing the pass still runs on the lane in force and a fall-through carrying `money: null` would be a way onto a paid lane nobody had authorised. Two rules keep the floor from becoming that same hole: it is **inclusive** (naming a lane admits it), and it **never excludes the lane in force** — a floor bounds where routing may *send* a pass, and excluding the lane the deployment is already on would either silently run the pass there anyway (making the setting a lie) or refuse a pass with nowhere else to go; the lane in force still answers to the wall and to the money guards, which is what makes the settings screen's routing row and the pass agree by construction. Autonomous work is therefore routed off a walled lane too — #173's attended/unattended asymmetry now lives only in the *refusal* (an attended pass is told why and held; an autonomous one is left on its lane to be refused in ~2s and parked) — and "no observation is not a closed gate" is what makes a lane with no quota telemetry admitted on **spend** rather than on the subscription's wall
- Parked runs re-check lanes on every sweep (issue #199): a run parked on a quota wall stops being stranded beside a lane that could serve it. The reducer's paused-run path resumed on exactly one condition — its clock — so authorising a paid lane a minute after a run parked changed nothing for five hours, and on a one-slot box a dependency chain stalled behind it. It gains a second: while the wall **still stands by its clock** (`now < resumeAfter`), a lane other than the walled one that can serve the run now resumes it there (`resumeRunOnLane`) instead of waiting. `src/lib/orchestrator/autonomy/paused-runs.ts` owns the gatherer and both resume executors (extracted from the sweep so they run over a real DB with the real `lanes.yaml` under test): each `PausedRun` carries the walled lane off its task row and a `laneFailover` ranked through the **same** `readLaneFailover` a refused pass is offered at the moment of its wall, with the walled lane excluded — so the two paths cannot disagree about which lane is cheapest, and so #174's cap and confirm-once press, evaluated *inside* that ranking, make a money-held lane simply never offered: unattended work still starts spending real money only under the day's confirmation and cap, and a null option means "stay parked" with no second reading of the guards. It is a lane move like any other: it counts against the same resume bound (judged **first**, before lane and clock — a run with no continuations left is never going to resume anywhere, so at the bound it exhausts to a human rather than moving again), it shares the clock-driven resume's body (lineage, session carry where the transcript survived, `resumeCount` bumped when decided, run left visibly `rate_limited` until the pass starts), it reserves a slot like any resume and is not held by the kill switch or the daily cap, and it is announced on the issue with the lane **and what it costs** — one sentence, `describeLaneCost` (`src/lib/lanes/lane-rate.ts`, a leaf the settings screen's rate formatter also lives in), which #176's failover announcement now reads too, quoting the ranking's own $/Mtok or saying the lane "declares no prices". Only while the clock stands by **more than the jitter window**, deliberately: once the window has reset the run's own lane is free again, so the ordinary jittered resume takes over, and a wall lifting inside that window is not worth paying a lane move to skip either (the move would buy at most the wait the jitter imposes); a clockless row (eligible now) never moves. The comment says the run *is resuming* there and that the lane is re-chosen as the pass starts, because the target is advisory and `tasks.lane` is the record. The target is advisory as a failover's is — `startTask` re-asks the ranking. The wall ordering of a *finishing* pass — degrade, then failover, then pause — is unchanged; a paused-run entry for a run decided by that path on the same tick is skipped. **Enforced limit (#217):** a move carries the session only between lanes on the same adapter — every declared lane runs the one `claude-code` adapter today, which is *why* every move so far has carried it; a move across two adapters starts again on the branch and says so (the harness bullet has the mechanism)
- Manual move of a parked run (issue #202): the operator can move a run parked on a quota wall onto a paid lane **now**, from its fleet card, for the case #199 does not cover — the ranking would *not* move it (most often because nobody has confirmed the day's real-money spend) and the run is gating everything behind it on a one-slot box. It is an operator action, so it is **attended**, and that changes exactly two things: the money guards are put in front of a human rather than silently holding (an unconfirmed lane is refused *naming the press*, a capped one *naming the cap*; the press itself waives neither, because the confirmation is the fleet's for the day and one card must not authorise it), and a refusal is **stated, never silent** — which lane a press would free, or why nowhere at all can serve the run (a missing credential by variable name, the pass kind's floor, a pin, a wall on the other lane too). `decideManualLaneMove` (`src/lib/orchestrator/autonomy/lane-move.ts`) is the one pure decision the route's `GET` (what would happen) and `POST` (do it) both make, over the **same** failover ranking the sweep re-reads every tick — read *whole* (`selectLaneFailover` / `readLaneFailoverSelection`, of which #176's `planLaneFailover` is now the winner-only reduction) because the reasons live in the losers, and `heldForMoney` is where "a press away" already lives. The bound is judged first, as the reducer judges it before the clock. Like #199's early resume it is only for a wall that **still stands**: past the reset (or on a clockless row) the run's own lane is free again and the jittered resume is minutes away, so a move would spend a continuation and be re-ranked straight back onto the free lane as the pass started — the reducer takes the ordinary resume there, and this refuses (`window-reset`) and says so. The move shares the early resume's body (`queueResumedPass`: lineage, session carry where the transcript survived, `resumeCount` bumped when queued, run left visibly `rate_limited` until the pass starts) and its wording (`laneMoveWording`, one builder for both moves, quoting `describeLaneCost`), so the issue thread cannot tell the operator's move from the sweep's on the money; the opening — who moved it — is the only thing that differs. The per-run facts both read come off one `pausedRunFacts`, so "read exactly as the sweep reads them" is structural. The card asks before it offers (`GET`), so the confirmation names the lane and its $/Mtok **before** any money is spent, and the `POST` decides again freshly because the fleet moves between the two. Under an `unconfirmed` refusal the card offers #174's fleet-level press where the operator stands — #173's at-the-keyboard shape, with the same prose saying it authorises unattended cash up to the cap until midnight — and then asks again, so the move is two deliberate presses (the fleet's day, then this run) rather than one card silently granting the day. The control is **absent** from every card but a paused run's (the route would refuse it "not parked", and a control that can only be refused is noise) and sits **outside the card's link** — the frame is its own element now, the anchor inside it — because a button in an anchor is invalid and a press must not also open the task. Nothing here touches orchestrator memory (#159): the handler runs on the app-router graph and everything the move needs is in the database
- Wall-triggered failover (issue #176): a refused pass **moves lanes instead of pausing**. `failOverRunLane` is asked in the reducer *after* #170's tier ladder (a rung down is free — the account still has quota — where a move may cost real money and will certainly cost a fresh conversation's worth of orientation) and *before* #168's pause, which becomes the fallback for when no lane is both available and permitted. Like both of them it spends neither an attempt nor an interruption, and it shares their `endRefusedPass` ordering; unlike the degrade it **carries the session**, so a move is lossless exactly as #169's resume is (and carries it only when the transcript actually landed — `--resume` against a session the fresh container never heard of fails the pass outright, which is why `queueNext` is handed `preserved`). It is bounded by `runs.resumeCount` against the same `maxResumesPerAttempt` a resume answers to: a move *is* a continuation of the attempt, so it counts there rather than getting a second number nobody would keep true, and past the bound the run pauses and #169's exhaustion hands the ticket to a human — which is what stops a run thrashing across lanes forever. A **reset-less** wall is the case this helps most: a pause needs a clock and had none, so before this such a pass took the ordinary path and spent one of the ticket's three attempts. The target lane is **advisory**, not a pin: the replacement pass re-asks the same ranking when it starts, so a window that lifted in the intervening half-minute sends it back to the cheaper lane, and `runs.lane`/`tasks.lane` still record where the work really ran because `startTask` writes them at pass start. Known boundary, deliberately not widened here: #171's admission gate and #174's pickup guards still read the **primary** lane's row rather than the lane routing would pick, so new *pickup* under a walled primary still waits where an in-flight run fails over — the gate is fleet-wide by construction and making it per-kind needs its own ticket

- Tier coverage and outcome by tier (issue #198): both are computed in `buildFleetView` (`FleetView.tiers`, a `TierView`), so the dashboard's Tiers panel (`src/components/fleet/tier-outcomes.tsx`) and the digest's Tiers section render one structure and cannot describe the fleet's routing differently. The unit is the **run**, never the task — a run whose tier changed mid-attempt (a degrade, a resume, a lane move) owns several task rows, and counting those would count one attempt twice — grouped once under `runs.model`, the tier the work actually ran at, with `degraded` on the row saying how many arrived there by the ladder rather than by a ticket's choice. The unit is in fact the **attempt** — the `(ticket, attempt)` pair — because a restart re-claims an interrupted run as a new row under the same attempt number and consumes nothing (#24), so counting rows would inflate the burn rate with the platform's own downtime; an attempt's rows are folded, read through the latest, charged every row's spend. Coverage is counted over the attempts *claimed* in the recent window (windowed by claim date, unlike the finish-dated ledger beside it), so the rows' attempts sum to `coverage.claimed`; nothing claimed reads as nothing, not as 0%. A row's `declared` counts only tickets that named *that* tier, so a run that declared heavy and fell to light is routed work on neither row. The derived wording — verdict summary, the no-tier label, pluralising — lives in `tier-prose.ts`, a type-only leaf both surfaces import, because the panel is a client component and a value import from the read model would pull its graph into the browser bundle. It reads `runs.declaredTier`, never `model`: the implement pass writes the *resolved* tier to `model` (the ladder needs a rung to step off and every later pass resolves through it), after which a fleet default and a declaration are indistinguishable — the ticket's "no migration needed" held for outcome-by-tier but not for coverage, which is why that one column exists, written once at claim and never rewritten

- The review tier is **derived, not chosen** (issue #201), and review is the **only** derived kind (issue #211): a review resolves to **one rung above the run's implement tier** (`tierAbove`, capped at the top of the vocabulary), decided in `resolveAgentModelChoice` — the one pure model-choice function every pass resolves through, which already received `runs.model` on every pass of a run and discarded it for the non-work kinds, so there was no new plumbing. A single fleet review tier cannot be right for both a one-line guard and a new state machine; deriving review *equal* to the implement tier was rejected because a ticket declaring `light` would buy itself a light gate. The reviewer's own fleet setting (`modelTierReview`) is a **ceiling** on the derivation when explicitly set — a stored override or a tier named in the field's **own** variable — and unset, the derivation runs free. Two things that look set are deliberately not a ceiling: the base `AGENT_MODEL` standing in for an unset `AGENT_MODEL_REVIEW` (`EnvDefault.inherited`) is the *implement* kind's setting and what an underived review falls back to — read as the review's ceiling it would cap every review at the implement tier in the commonest configuration, the rejected design by the back door — and a lane's default over an unset field (#175) is what an underived pass runs, not a bound anyone chose. The reading is one function, `tierDerivation` (`free` / `capped` / `pinned`, in `settings-resolver.ts`), that the pass and the settings screen both resolve through, so the screen is *handed* the rule (`SettingFieldView.derived`) rather than restating it; it reads the field alone, because the field is the reviewer's own — so it is a hard cap (a review tier set low caps a heavy ticket's review below its implement pass — the accepted consequence) and a raw model id pinned in it is run as pinned with nothing derived. A run with no resolved implement tier derives nothing and resolves exactly as before; triage and interactive derive nothing. **Repair runs at the run's own tier** (issue #211): #201 stepped it up too, on the argument that a repair is a second attempt at work that already failed — but that is not what the `repair` kind is. Both passes queued under it (integration repair #54, merging the default branch into a CONFLICTING PR; CI repair #130, making a red rollup green) are triggered by `main` moving under a parked PR, not by the work being judged wrong, and fixing a merge conflict on the fleet's most expensive model spends the tier the fleet is most constrained on. So a repair resolves exactly as an implement pass does — the run's tier (`runs.model`) wins, and with none the implement setting answers, a pinned raw model id passing through; `MODEL_TIER_FIELD_BY_KIND.repair` stays `modelTierImplement`, the Implement row is a chosen tier for both kinds and a ceiling on nothing, and the repair-only branches (`floorsAtRunTier`, `strongerTier`, the work-kind guard on `tierDerivation`'s pinned rule) are gone rather than dead. The fix-up a request-changes verdict triggers — the case #201's sentence did describe — is a follow-up turn in the same implement container, never a repair pass, and its tier is untouched; stepping it up is a new mechanism, decided against on #211 until outcome-by-tier shows standard attempts failing on review cycles. A repair pass still never writes `runs.model` (`startTask`): that column is the tier the *implement* pass ran at — what a repair runs at, what the review derives from, the rung the quota ladder steps off (#170, one-way) and the group outcome-by-tier files the run under (#198) — while the tier a pass actually ran at is on its task row (`tasks.tier`, written at pass start for every kind). **Known boundary, filed as #207**, whose repair half #211 made moot: the ladder reads the *run's* tier as the walled pass's starting rung, so a *review* walled on a tier-scoped window steps `runs.model` from the implement tier rather than the tier it actually ran at, and a degraded run's review derives one rung back up into the window the ladder stepped off. On the settings screen only the Review row describes itself as a ceiling, and its effective line says "ceiling X on review" rather than "runs X"

- Restart recovery (issue #24): boot marks claimed/implementing/reviewing runs that own a `running` task as `interrupted` (a run holding a stored review verdict is left for the verdict path instead; gated/blocked runs wait on a human, not a lost turn). The sweep then re-claims the ticket **without** consuming an attempt — interruptions are counted from `interrupted` ledger rows, separately from failed attempts, and bounded by `MAX_INTERRUPTIONS_PER_TICKET` (5, in `budgets.ts`); past the bound the ticket is routed `ready-for-human` like exhaustion. The reaper never removes a container whose task belongs to a live run. Boot also **finalizes dangling runs** (issue #106): a run left non-terminal with no PR, no stored verdict, and all tasks terminal is driven to `failed` so a pre-fix ghost `running` card self-heals on the next restart — the durable fix drives such runs terminal at pass completion in `decideNext` (`finalizeEmptyPass`), this only backfills runs stranded before it landed
- Boot also **re-adopts parked containers** (issue #136): `activeTasks` is process memory whose only writer was `startTask`, and queue step 2 — the sole deliverer of a queued user message — iterates it, so a restart while a run sat `blocked` made the owner's answer permanently undeliverable. Boot now reconstructs the entry as parked/idle for every `blocked` task whose container still exists (holding no slot, so the existing delivery path resumes it on the next poll); a container the daemon has definitively lost drives its run `interrupted` instead (no attempt consumed, bounded by `MAX_INTERRUPTIONS_PER_TICKET`) and the question plus any undelivered answer is posted to the issue. A daemon that does not answer decides nothing — the run stays blocked and the next boot asks again. The pure decision is `planParkedAdoption` (`src/lib/orchestrator/parked-adoption.ts`); a user message left undelivered past `UNDELIVERED_ANSWER_MINUTES` (10) raises a fleet-health card + one Discord ping

- Run migrations: `npx drizzle-kit push`
- **Adding a generated migration:** set the new journal entry's `when` to at
  least one day past the prior entry's (drizzle skips same-day entries it
  believes it has applied), and `rm local.db*` before running tests — a stale
  local DB makes the runs-ledger and parallel-worker migration tests fail on
  code that is actually correct. A migration that *renames* a column (issue
  #175 renamed `quota_state.id` to `lane`) is applied faithfully by the
  production path, which runs `migrate()` over the journal; `drizzle-kit push`
  may instead recreate the table and drop its rows, so prefer `migrate()` on
  any local DB whose contents you care about. A hand-written migration still
  needs its `drizzle/meta/NNNN_snapshot.json` beside the `.sql`: `migrate()`
  never reads a snapshot, so nothing local fails without one, but the *next*
  author's `drizzle-kit generate` diffs against the last snapshot and re-asks
  about a rename that already shipped — and either answer puts a second
  `RENAME COLUMN` into the next migration, which is a boot failure rather than
  a caught error because `migrate()` runs at module load in `src/db/index.ts`
- Generate migrations: `npx drizzle-kit generate`
- DB client: `import { db } from "@/db"`
